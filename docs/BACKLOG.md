# Backlog

For the owner and developers: what is left to build, in order, and what each item needs before it can start.

What [ADMIN_GUIDE.md](ADMIN_GUIDE.md) and [API.md](API.md) describe is built. This page lists what is not. Each item says what it **needs** before it can be built: a decision from the owner, an outside account or contract, equipment to test with, or only code. What staff do meanwhile is in [ADMIN_GUIDE.md › Not built yet: what to do meanwhile](ADMIN_GUIDE.md#not-built-yet-what-to-do-meanwhile). Going live with a real business is in [GO_LIVE.md](GO_LIVE.md).

## 5. Live updates and the outbox

The staff screens are live: a change made on one screen appears on every other open screen that shows it within about a second, and no screen asks the server every few seconds any more; most keep a slow safety net of a minute ([ARCHITECTURE.md › Live updates](ARCHITECTURE.md#35-live-updates)). That covers the restaurant's kitchen display, table requests, the POS, the captain app, deliveries, the collection display, the dashboard, reservations, the floor, the bell and notifications and the time clock, and in the other businesses the token queue, the clinic and lab workspaces with the lab's orders, the salon calendar, my tasks, the jeweller's rate board and the bell. What is left:

| Item | Where it stands | What it needs |
| --- | --- | --- |
| **Messages from the outbox** | Every posting of a business writes an event (`business_events`) in the same transaction, so nothing is lost; the live screens hear of each one, but nothing sends them outside, and the restaurant's own postings write no events ([ARCHITECTURE.md §9.3](ARCHITECTURE.md#93-plans-d-e-and-f), plan E, step 3). | A publisher process that reads unsent events in order and marks them sent, with retries and a dead-letter record, and the messaging provider in [§1](#1-outside-integrations). How to connect a consumer is in [ARCHITECTURE.md › Add an outside integration through the events outbox](ARCHITECTURE.md#88-add-an-outside-integration-through-the-events-outbox). |
| **The guests' pages** | They still ask: a table's QR page every 6 seconds while it waits for the staff and every 20 while the food is made, an online order's status every 8 and 20, a booking request every 20 until the restaurant answers. A guest has no session to scope a live stream by: a table's QR code is shared by everyone at the table, and an order's or a booking's link is its only key. | A key a stream can be scoped by safely without a staff login (short-lived and signed, for one order or one table's visit), limits per address for streams with no login, and the owner's go-ahead for an open connection per guest's phone; then code. |

## 8. Needed in the code before go-live

- **The session token.** The staff app keeps it in the browser's `localStorage` (`rmp_token`). Decide before production whether it stays there.

With several API processes behind a load balancer, those need a shared cache or sticky sessions.
- **Plan F, the migration baseline** ([§6](#6-structure-work)). When no more schema changes are expected, new installs run one baseline file instead of every migration.
